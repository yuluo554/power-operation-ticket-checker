# 04 模块详细设计

> M0 定稿骨架版：schema 与接口为本轮**已实现并锁定的 v0.1**；标注（Mx）的部分为计划内容，随里程碑细化为 v0.2+。

## 1. 统一中间表示：票面参数卡（TicketCard）v0.1

所有票种解析后统一为此结构；规则引擎只消费它，不接触原文。

```python
Evidence(region, quote)            # 证据：票面区域(header/body/signature/...) + 原文逐字摘录
FieldValue(value, confidence=1.0, evidence=None)   # 字段包装：值-置信度-证据
OperationStep(no, action, evidence=None)           # 操作票逐项序列
TicketCard(
    ticket_type,                   # 票种代码，见下表
    fields: dict[str, FieldValue], # 通用字段（编号/任务/时间/人员/安全措施条目…）
    operation_sequence: list[OperationStep],
    warnings: list[str],           # 解析告警（丢弃非法值等，可追溯）
)
```

票种代码表（**既定口径**，M2 起全仓统一）：

| 代码 | 票种 |
|---|---|
| `operating` | 变电站倒闸操作票 |
| `line_operating` | 电力线路倒闸操作票 |
| `work_first` | 变电站（发电厂）第一种工作票 |
| `work_second` | 变电站（发电厂）第二种工作票 |
| `line_work_first` | 电力线路第一种工作票 |
| `line_work_second` | 电力线路第二种工作票 |
| `emergency_repair` | 事故紧急抢修单 |

## 2. 解析层（parse）

流程：**清洗 → 票种路由 → 槽位抽取 → 合法性校验 → 参数卡**。

1. `cleaning.normalize_text`：CRLF→LF、去零宽/全角伪空格（M2 扩展：字符定位伪空格、多行聚类）。
2. 票种路由 `detect_ticket_type`：关键词门控（"倒闸操作票"/"第一种工作票"/…），无匹配 → `ParseError("无法识别票种")`；匹配但解析器未注册 → `ParseError("解析器未实现(M2)")`。
3. 槽位抽取：每票种一个 parser，正则+槽位；抽取值必须带证据（区域+原文摘录）。
4. 合法性校验：日期/数值格式不合法即**丢弃该值+记 warnings**，不得带病入卡。

M2 计划：7 票种全覆盖；安全措施条目结构化；许可/间断/转移/终结环节人员时间。M4：LLM 兜底抽取走同一参数卡出口。

## 3. 规则引擎（rules）

### 规则 JSON schema（**既定口径**，知识库入库格式）

```json
{
  "id": "R-OP-002",
  "name": "操作时间顺序合法",
  "check_type": "time_order",
  "applies_to": ["operating"],
  "basis": {"standard": "Q/GDW 1799.1-2013", "clause": "…", "quote": "…", "status": "待核对"},
  "level": "形式合规",
  "risk": "一般",
  "suggestion": "核对操作开始/结束时间填写是否颠倒。",
  "params": {"start": "start_time", "end": "end_time"}
}
```

- `basis` 为必填：无出处的规则**不得落库**；`status ∈ {已核对, 待核对}`，待核对不得以确定语气写进结论。
- `applies_to` 为**类目门控**：引擎在**全部** check_type 上先过门控再分派（防跨票种误查，conditional/checklist 分支也不例外）。

### check_type 分派表

| check_type | 校核内容 | 状态 |
|---|---|---|
| `required_field` | 必填项非空 | ✅ M0 已实现（引擎通路验证） |
| `time_order` | 时间先后逻辑（开始<结束；M3 扩展许可落区间/终结闭环） | ✅ M0 已实现（引擎通路验证） |
| `process_signature` | 签发→许可→监护→间断/转移→终结签字齐全（M3） | 计划 |
| `ticket_type_match` | 票种与工作内容/停电需求匹配（M3） | 计划 |
| `measure_coverage` | 安全措施四要素+组织五制覆盖（M3） | 计划 |
| `five_prevention` | 五防形式化检查（M3，逐条挂规范出处） | 计划 |
| `consistency` | 电压等级/双重名称/人员角色/操作项与措施互证（M3） | 计划 |

未知 check_type：跳过+warnings 记录（防御性，不让坏规则炸引擎）。

### 结论模型（Conclusion）

```python
Conclusion(rule_id, name, verdict, risk, basis, evidence, suggestion)
verdict ∈ {"合规", "不合规", "待人工确认"}
risk    ∈ {None, "低", "一般", "较大", "重大"}     # 仅不合规时有值
```

多值/低置信度/待核对依据 → 一律"待人工确认"，不硬判。

## 4. 知识库（knowledge，M3）

三层：`data/knowledge/raw/`（规范原文+来源台账）→ `chunks/`（条文块，纯 Python 余弦检索）→ `rules/`（机器可读规则 JSON）。每条挂 `standard+clause+channel+status`；检索接口签名 M3 定稿后列入既定口径。

## 5. 编排与交付（pipeline / report / web，M5）

- `pipeline.run_pipeline(text) -> {card, conclusions, summary}`：解析→校核→汇总，CLI 与 Web 共用。
- 报告结构：结论汇总 → 分级问题清单 → 逐条证据（含原文摘录）→ 整改建议 → 签署栏；"待人工确认"独立成节。
- Web：FastAPI 上传→参数卡→结论→报告预览；前端 vendor 本地化，0 外链断言进测试。

## 6. 基准评测（eval，M4）

| 脚本 | 指标 | 口径 |
|---|---|---|
| `parse_f1` | 字段级 P/R/F1 | 生成器真值 vs 解析结果；真值语义 expect/also_expect 按"全部非 pass 集合"对账 |
| `endtoend` | 检出率 / 误报率 / 判定准确率 | 植入缺陷 vs 规则命中；无植入缺陷报不合规即误报 |

门槛：F1≥0.95、误报 0；零 API 依赖；指标入 README。接口签名定稿后列入既定口径。
